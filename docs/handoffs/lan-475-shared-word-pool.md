# LAN-475 단어 음성 (억양, 단어) 공용 풀 — 1단계 백필·풀 QA 실행서 (2026-09-24)

단어 음성의 옛 S3 키는 `{표현id}/{억양}/word/{순서}/{해시}.mp3`라 경로에 표현 id가 들어가,
같은 단어가 표현마다 따로 저장돼 있다. 해시는 이미 (모델·보이스·텍스트·포맷)으로만 계산되므로
같은 해시는 같은 소리다. 1단계는 **기존 객체에서 대표를 골라 공용 자리로 복사만** 한다 —
새 합성도, 옛 키 삭제도 없다.

## 되돌릴 수 없는 작업 두 가지 (먼저 읽을 것)

버킷 `landit-content-982529430654`에는 **버저닝이 없다**. 다음 둘은 복구 수단이 재합성뿐이다.

- `check-pool --publish-fixes --execute`의 **공용 키 덮어쓰기**. 그 키 하나를 수백 개 표현이
  함께 쓴다(`the`는 852개). 잘못 올리면 한 번에 퍼진다.
- 4단계의 옛 키 삭제 (이 문서 범위 밖, V126 prod 검증 후).

백필의 복사는 새 키를 만들 뿐이라 이 범주가 아니다.

## 1. 단어 목록 뽑기 (`--words` 입력)

공용 풀의 해시를 단어 텍스트와 이어 붙이는 데 쓴다. DB가 "지금 실제로 쓰이는 단어"의 기준이다.

```sql
SELECT DISTINCT a.accent_locale, w.value ->> 'word' AS word
FROM expression_pronunciation_asset a,
     LATERAL jsonb_array_elements(a.words) AS w
ORDER BY 1, 2;
```

결과를 `{억양}<탭>{단어}` 한 줄씩으로 저장한다 (psql이면 `\copy ... TO 'dev_words.tsv'`).
단어의 대소문자·문장부호·앞뒤 공백은 해시에 들어가므로 **손대지 않는다**.

## 2. 백필 (dry-run → 실행)

```bash
python3 -m scripts.expression_pronunciation_audio backfill-word-pool \
  --bucket landit-content-982529430654 \
  --prefer-expression-ranges 982-1938,2259-3000 \
  --words dev_words.tsv --unmatched drop \
  --output word-pool-index.json --boto3
```

- `--prefer-expression-ranges`는 QA를 받은 배치(3·4)의 표현 id 구간이다. 대표를 그쪽에서
  먼저 고르고, 같은 조건이면 표현 id·단어 순서가 작은 쪽을 쓴다 → **재실행해도 같은 대표**가 나온다.
  (실데이터 86,562키로 확인: 입력 키 순서를 섞어도 색인 바이트가 동일하다.)
- `--unmatched drop`: 어떤 단어로도 만들어지지 않는 해시 **12개**를 풀에서 뺀다. 표현
  1942·1945·1946에서 예문이 수정되며 버려진 옛 음성이다(같은 단어 순서에 키가 둘). 기본값은
  `stop`(중단)이고 `keep`은 단어 없이 풀에 넣는다. **`keep`으로 만든 색인으로는 `check-pool`을
  돌릴 수 없다**(단어 텍스트가 없으면 검사할 기대값이 없다). 그 경우 백필이 그렇다고 알려 준다.
- 색인은 스키마 버전 **2**다(항목마다 `published`가 있다). 그 필드가 없는 옛 색인은
  `check-pool`도 V126도 받지 않는다 — 백필로 다시 만들면 된다.
- 게시하려면 `--execute`를 붙인다. `--publish-index`를 함께 주면 색인을 S3
  `word-pool/{해시}.json`에도 올린다 — 2단계 V126의 허용 목록이 이 키에서 나온다.
- 출력의 `published=N/M`은 **S3 실물 목록에서 받은 수**다. dry-run이면 `0/10494`으로 나오고,
  그 색인은 `--publish-index`가 거부한다. **`published`가 전부 차지 않은 색인을 V126의
  허용 목록으로 쓰면 파일 없는 URL을 허용하게 된다.**
- 복사는 같은 버킷 안 서버 사이드 `copy-object`(`--metadata-directive COPY`)라 Cache-Control과
  `audio-sha256` 메타데이터가 그대로 옮겨 오고, 복사 직후 원본과 head를 대조한다.
- **이미 공용 자리에 있던 항목(`reused`)도 `--execute`면 원본과 전수 대조한다.** 어긋나면
  멈춘다. 풀 QA가 고쳐 올린 객체(`replaced-by: lan-475-pool-qa` 메타데이터)는 원본과
  달라지는 것이 정상이라 대조에서 빼고, **몇 개를 뺐는지 출력한다**
  (`reused N verified against source, M skipped (QA replaced)`).
- 비용: 백필이 한 번 끝나면 10,494개가 전부 `reused`가 되므로, **기본 `--execute` 재실행도
  항목당 head 2회 = 약 21,000회**를 돈다(첫 실행은 reused가 0이라 공짜다).
  `--verify-existing`은 그 위에 **전 항목**을 한 번 더 훑는다. 풀을 손댄 적이 있을 때만 쓴다.

**중간에 죽으면 그냥 다시 돌리면 된다.** 키 목록을 새로 읽어 복사 대상을 다시 계산하므로
멱등하다. 실패 시 `copied=N/M before failing`이 나오는데, 이 N은 **S3에 실제로 도달한
복사 호출 수**다(결과를 꺼낸 수가 아니다). 남은 작업은 취소한다 — 원본 하나가 빠진 걸로
나머지 수천 건을 더 복사하지 않는다. reused 대조에서 터지는 경우에도 복사 진행분은 그 앞에
이미 출력돼 있다.

## 3. 풀 QA — 반드시 두 번에 나눠서

### 3-1. 먼저 게시 없이 돌려 불합격 목록을 읽는다

```bash
python3 -m scripts.expression_pronunciation_qa check-pool \
  --index word-pool-index.json --work-dir pool_qa --report pool_qa/qa_report.json \
  --bucket landit-content-982529430654 \
  --workers 4 --backend mlx --boto3 \
  --resynth --max-resynth 6 --keep-failed-dir pool_qa/failed
```

- **`--work-dir`은 색인마다 새 폴더를 쓴다.** 작업 폴더의 mp3 경로 형식은 `generate`·`check`
  명령과 같아서, 옛 배치 폴더를 재사용하면 남의 음성이 섞인다. 정체를 증명할 수 없는 로컬
  파일이 있으면 도구가 멈추고, **원인별로 다른 메시지**를 낸다 — 기록이 아예 없다(남의 파일,
  지울 것) / 다른 색인의 기록이다(폴더를 나눌 것) / 기록보다 파일이 최신이다(재합성이
  중단된 것, 지워도 안전하다) / S3에 `audio-sha256`이 없어 내용 대조가 안 되는데 출처도
  모른다(지우고 다시 받을 것).
- (억양, 단어) 단위로 **한 번씩만** 돈다. 852개 표현이 쓰는 `the`도 한 번만 검사한다.
- QA 이력이 있는 대표 7,653개는 **무음 검사만** 한다(복사 사고를 잡는 그물). 이력이 없는
  2,841개만 Whisper 전사까지 본다. `--recheck-qa-verified`를 주면 전부 전사한다.
  색인의 모든 항목이 무음 검사 대상이면 Whisper를 아예 띄우지 않는다.
- 음성은 공용 키에서 받고, 아직 복사 전이면 원본 키에서 받는다.
- 풀 state는 `pool-state.json`에 따로 쓴다. 같은 폴더의 `state.json`(표현 단위 작업용)은
  건드리지 않는다.
- 불합격 줄에는 그 단어를 쓰는 표현 수(`used_by`)가 함께 나온다. 852개가 쓰는 단어와 한
  표현만 쓰는 단어는 손볼 급이 다르다.

여기서 **`withheldFailures`를 반드시 확인한다.** 재합성을 다 쓰고도 불합격으로 끝난 것들이다.
게시하지 않고 보류한다 — 사람이 듣고 골라야 한다(LAN-471의 `listen_final40` 방식).

### 3-2. 확인이 끝나면 게시한다

게시 전에 3-1 출력에서 세 가지를 눈으로 확인한다.

| 확인 | 기대값 | 아니면 |
| --- | --- | --- |
| `missingRemoteSha` | 0 | S3에 `audio-sha256`이 없는 객체가 있다는 뜻. 그 항목은 내용 대조를 못 하니 따로 본다 |
| `withheldFailures` | 0이거나, 목록을 직접 듣고 판단 | 재합성으로도 못 고친 것들이다. 게시되지 않는다 |
| `carriedOverFixes` | 3-1에서 고친 수와 같다 | 다르면 work-dir에 예상 밖의 파일이 있다는 뜻 |


같은 명령에 `--publish-fixes --execute`를 붙여 다시 돌린다.

- 3-1에서 만든 수정본은 **그대로 남아 있다.** 다시 받아 덮어쓰지 않는다(`carriedOverFixes`).
- 게시 대상은 **"지금 로컬이 S3와 다르고 합격한 단위"**(`pendingPublish`)다. 불합격은 올리지 않는다.
- `missingRemoteSha`가 0이 아니면 그 항목은 S3에 `audio-sha256`이 없어 "로컬이 원격과 같은지"를
  판정할 수 없다는 뜻이다. 게시 대상에서만 빼고 검사는 정상으로 진행하며, 3-1과 3-2를 같은
  폴더에서 돌려도 막히지 않는다. 그 항목은 따로 눈으로 본다.
- 게시 도중 실패하면 `publishError`와 **그때까지 S3에 올라간 키 목록**을 출력하고 멈춘다.
  put은 됐는데 결과 검증만 어긋난 키도 **이미 바뀐 것이므로 목록에 포함**되고
  `unverifiedKey`로 따로 표시된다(내용을 직접 확인할 것). 원인을 고친 뒤 같은 명령을 다시
  돌리면 된다(멱등).
- 게시 후 CloudFront는 immutable로 캐시하므로 **교체한 키만** 무효화한다(출력의 `replaced` 목록):

```bash
aws cloudfront create-invalidation --distribution-id E15GMGRWJSHMCU \
  --paths /content/expression-pronunciation-audio/word/EN_AU/<해시>.mp3 ...
```

## 다음 배치 생성 (LAN-561 적용 후)

파이프라인이 단어를 (억양, 단어) 단위로 다룬다. 생성 명령은 그대로지만 **`--reuse-s3-bucket`을
반드시 준다** — 공용 자리에 이미 있는 단어는 합성하지 않는다.

```bash
python3 -m scripts.expression_pronunciation_audio generate \
  --source tts_source.json --work-dir work \
  --reuse-s3-bucket landit-content-982529430654 --boto3 --workers 4
```

출력에 `synthesized=` / `reused_from_s3=`가 찍힌다. LAN-471 배치를 지금 규칙으로 돌리면
단어 16,167개 중 새로 만들 것은 984개다.

- **옛 지침 "신규 id면 `--reuse-s3-bucket`을 빼라"는 더 이상 맞지 않는다.** 표현별 경로 시절
  이야기다 — 그때는 새 표현 id면 옛 키가 절대 없어 head 호출만 낭비였다. 지금 빼면 이미 있는
  단어를 전부 다시 만든다.
- 작업 폴더의 `state.json`은 스키마 2다. 옛 파일(스키마 1)은 거부한다 — 자산별로 적혀 있어
  같은 단어의 형제 행이 낡은 sha를 들고 있고, 그대로 읽으면 재합성 판정이 어긋난다.
  옛 작업 폴더는 재사용하지 말고 새로 만든다.
- `verify-accent`는 같은 (파일, 대조)를 한 번만 판정한다. 한 단어 클립에 서로 다른 대조가
  붙어 있으면 중단한다 — 클립은 하나인데 기대값이 둘이면 어느 쪽도 만족시킬 수 없다.

## 유의점

- **풀을 고쳐도 사용자에게는 아직 옛 소리가 나간다.** DB의 단어 URL이 여전히 옛 키를 가리키기
  때문이다. 공용 키 교체가 실제로 앱에 반영되는 것은 **V126이 prod에 붙은 뒤**다. 그전까지는
  옛 키도 함께 고쳐야 사용자 경험이 바뀐다(옛 키 교체는 이 도구 범위 밖).
- 자산 id는 `{표현id}/{억양}/word-{순서}` 형식을 그대로 쓴다(대표를 뽑아온 원본 키 기준).
  landit-ai `scripts/prune_accent_contrasts.py`가 이 형식을 정규식으로 파싱하기 때문이다.
- 같은 자산 id가 색인에 두 번 나오면 `check-pool`이 즉시 멈춘다(해시까지 같은 완전 중복도
  막는다 — 판정이 서로 덮어써 한쪽이 보고서에서 사라진다). `--unmatched drop`으로 만든
  색인에서는 생기지 않는다. 검사 후에도 자산 id 집합이 색인과 같은지 다시 대조한다.
- 색인의 단어 텍스트로 해시를 다시 계산해 색인의 해시와 다르면 멈춘다. 단어 목록과 S3가
  어긋난 채로 검사·교체가 진행되는 것을 막는다.
- 3단계 예고: 억양 대조 문제 문자열은 landit-ai가 `(표현id, 억양, 순서, 단어)`로 위치를
  찾는데, 공유 클립의 문제는 **대표 표현 하나로만** 보고된다. 같은 단어를 쓰는 다른 표현의
  대조까지 정리하려면 그 도구 쪽도 단어 단위로 넓혀야 한다(현재 데이터에는 같은 단어가
  표현마다 다른 대조를 갖는 경우가 0건이라 당장 문제는 없다).
- 1단계는 **추가만** 한다. 옛 단어 키 69,531개 삭제는 V126이 prod에 적용·검증된 뒤 4단계에서
  한다.
